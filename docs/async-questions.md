# 비동기 질문과 LLM 처리 큐

문서 질문은 서버에 저장한 뒤 HTTP `202 Accepted`와 `request_id`를 즉시 반환합니다. 화면에는 **처리 대기 중 → 답변 생성 중 → 결과**가 표시됩니다. 접수 후에는 다른 질문을 하거나 화면을 이동해도 서버 처리가 계속되며, 다시 방문하면 내 질문 기록에서 이어 볼 수 있습니다. 생성 중인 결과는 2초 간격으로 조회합니다.

현재 배포 구조는 데이터 디렉터리마다 RAG 프로세스 하나를 실행하고 `service.lock`으로 중복 실행을 차단합니다. 이에 맞춰 외부 브로커를 추가하지 않고 SQLite WAL 기반의 영속 메시지 큐를 사용합니다. 대기 요청은 DB에만 보관하고 3개의 소비자가 실행 가능한 요청을 접수 순서로 가져갑니다. 메모리에 대기 Future를 무제한 생성하지 않습니다.

일반 질문, 회의 발화 분류, 회의 답변 생성, 연결 검사, 프롬프트 테스트가 하나의 최대 **3개** 처리 슬롯을 공유합니다. 일반 질문은 작업 전체에 슬롯을 예약하므로 실제 LLM 동시 호출 수는 3개 이하입니다. 기존 회의 PQ/SQ 스케줄링은 유지하지만 우선 처리 경로도 이 상한을 넘지 않습니다. 로컬 검색 자원이 사용 중이면 질문을 다시 대기시키며, 사용자에게 재전송을 요구하지 않습니다. 모델 오류는 기록에 실패 사유와 함께 남기고 다음 요청을 처리합니다. 관리자 연결 검사와 기존 동기 회의 분석 API는 슬롯이 모두 사용 중이면 기존처럼 busy를 반환합니다.

질문의 자료 버전은 접수 시점에 고정하고 처리 중 해당 버전의 삭제를 막습니다. 실행 시 계정 권한과 자료 접근 권한, 외부 전송 동의를 다시 확인합니다. 질문 조회는 기존 계정별 접근 제어를 사용합니다. 처리 도중 워크스페이스가 삭제되면 늦게 도착한 결과가 기록을 다시 만들지 않습니다.

## API

- `POST /api/rag/workspaces/{wid}/questions`: 기존 질문 본문을 보내면 `202`와 질문 결과 형태의 접수 기록을 반환합니다. 처음에는 `status=queued`입니다.
- `GET /api/rag/history/{request_id}`: `result.status`가 `queued` 또는 `processing`이면 계속 조회하고, 그 밖의 상태면 완료 결과를 표시합니다. 관리자 조회에는 `?scope=all`을 사용할 수 있습니다.
- `GET /api/rag/workspaces/{wid}/questions`: 자신의 최근 질문과 검색 기록입니다.
- 선택 헤더 `Idempotency-Key`: 같은 계정·워크스페이스에서 같은 키와 본문을 보내면 기존 기록을 반환합니다. 같은 키에 다른 본문을 보내면 `409 IDEMPOTENCY_CONFLICT`입니다. 보관 기간 내의 기록에 적용되며 프록시에서도 헤더를 전달합니다.

기존 POST 응답을 최종 답변으로 사용하던 클라이언트는 접수 후 조회 방식으로 변경해야 합니다. 프론트엔드와 저장소의 질문 API 테스트 및 RAG smoke 호출은 이 방식으로 갱신했습니다. 문서 검색 API는 기존 동기 응답을 유지합니다.

## 재시작과 배포

정상 종료에서는 새 작업을 시작하지 않고 진행 중인 요청을 마무리합니다. 강제 종료 시 대기 요청과 처리 중이던 질문은 다음 시작에서 자동으로 다시 실행합니다. 외부 모델이 답변한 직후 결과 저장 전에 중단된 경우 외부 호출은 반복될 수 있습니다(at-least-once). 사용자 기록은 원래 `request_id` 한 건에 갱신됩니다.

스키마 8→9 마이그레이션은 큐 입력·멱등 키·재시도 시각 컬럼과 인덱스를 추가하며 기존 기록을 유지합니다. 배포 전 서비스를 중지하고 실제 RAG 데이터 디렉터리의 `registry.sqlite`를 백업하세요. WAL 파일이 남아 있으면 SQLite backup API로 일관된 백업을 생성하거나 데이터 디렉터리 전체를 함께 백업합니다. 새 백엔드와 빌드된 프론트엔드를 함께 배포한 뒤 서비스를 시작하면 마이그레이션과 큐 복구가 실행됩니다. 이전 코드로 롤백할 때는 중지 후 이전 코드와 스키마 8 백업을 함께 복원해야 하며, 백업 이후 접수된 요청은 그 백업에 포함되지 않습니다.

이 큐와 동시 처리 상한은 현재 단일 RAG 프로세스 배포에 적용됩니다. 여러 호스트의 RAG 프로세스로 확장할 때는 공유 브로커 및 분산 슬롯 제한이 필요합니다.

## 검증

`rag/tests/test_question_jobs.py`에서 느린 모델을 고정해 8명의 요청 중 3건 실행·5건 대기, HTTP 즉시 반환, 작업 중복 방지, 모델 오류 후 후속 처리, 재시작 복구, 권한 회수, 외부 전송 동의 철회, 회의 분석과의 공통 상한을 검증합니다. `scripts/question_queue_ui_smoke.mjs`는 합성 API로 접수 후 추가 질문, 새로고침 복원, 처리 상태 갱신 및 기록 화면을 확인합니다. 실제 모델 처리 시간 측정과는 구분됩니다.
