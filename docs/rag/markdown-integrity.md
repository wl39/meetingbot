# 서버 측 Markdown 구간 표시 설계

## 변경 이유와 처리 주체

이전 구현은 원문 전체를 브라우저로 보내 구조를 해석했다. 검색 조각의 문법 손상은 해결했지만, 큰 문서를 여러 검색 결과에서 동시에 조회할 때 전송량·브라우저 메모리·파싱 비용이 컸다. 이 경로는 제거했다.

**업로드 문서의 Markdown 파싱·구조 경계 판별·범위 확장·페이지 생성은 Python 서버에서 수행한다. LLM을 호출하지 않는다.** 브라우저는 서버에서 받은 작은 HTML 페이지를 추가로 안전성 검사한 뒤 표시한다. 짧은 생성 답변을 표시하는 `react-markdown`은 별도 용도로 남아 있다.

## 1. 문서 버전당 한 번 준비

신규 문서는 등록 처리 시, 기존 문서는 첫 열람 시 준비한다.

1. 검색 당시의 불변 문서 버전을 서버에서 읽는다.
2. `markdown-it-py`와 GFM/각주 플러그인이 전체 문법·전역 참조 정의·블록 위치를 읽는다.
3. 제목·앵커·블록 시작/끝 줄·검색 청크 범위와 렌더링 결과를 문서별 SQLite 파일에 저장한다. 원문 줄 번호 보기용 UTF-8 데이터와 줄 오프셋도 저장한다.
4. 24 KiB를 넘는 블록은 서버에서 HTML 구조를 유지한 페이지로 분할한다. 표 헤더·목록 번호·코드/강조의 여닫는 태그를 보존한다. 큰 표 셀은 빈 자리 셀을 함께 넣어 열이 옆으로 밀리지 않게 한다.
5. 임의 HTML은 표시 대상에서 제외하고, 외부 이미지는 설명만 표시한다. 서버 허용 목록으로 태그·속성·URL을 정제한다.

이 작업은 별도 프로세스에서 실행한다. 동시 생성은 서버 전체에서 1개로 제한하고, 60초가 지나면 종료한다. 생성 중 파일은 공개하지 않고 완료 후 원자적으로 교체한다. 프로세스가 끝나면 파싱 메모리도 반환된다. 상주하는 전문 AST 캐시는 없다.

**비용이 사라지는 것은 아니다. 최초 서버 처리와 추가 디스크 저장 비용으로 옮긴다.** 원문 구조를 한 번 파악해야 멀리 떨어진 코드 펜스·참조 링크·각주를 정확히 처리할 수 있다.

## 2. 조회할 때: 앞뒤 1 → 2 → 4 → 8 청크

사용자가 제안한 지수 확장을 사용하되, 매 단계에서 원문을 재전송하거나 다시 파싱하지 않는다.

1. 근거 ID가 가리키는 검색 청크를 찾는다.
2. 앞뒤 1개 청크의 줄 범위를 조회한다.
3. 저장된 구조 경계와 비교해, 검색 내용을 포함하는 블록의 시작·끝이 범위 안에 들어오는지 확인한다.
4. 부족하면 앞뒤 2개 → 4개 → 8개로 늘린다. 최대 반경은 128개다. 필요한 블록이 응답 크기 상한보다 크면 무한 확장하지 않고 페이지로 전환한다.
5. 블록 경계가 확인되면 **검색 내용에 필요한 최소 블록**만 반환한다. 확인에 사용한 주변 청크를 전부 보내지는 않는다.

원래 제안에서 ‘문법 검사’를 ‘이미 검증한 원문 구조 경계 확인’으로 보강했다. 코드 블록 내부의 `# 제목`이나 표 본문만 잘라 파싱해도 오류 없이 다른 문법으로 해석될 수 있기 때문이다. 정상적으로 파싱됐다는 사실만으로는 안전한 경계를 증명할 수 없다.

실제 64–69줄 레시피 목차 근거는 헤더를 포함한 58–69줄 표로 표시된다. 검색 점수·근거 ID·인용 위치·모델에 제공되는 기존 검색 조각은 변경하지 않는다.

## 3. 전송·클라이언트 자원 제한

| 항목 | 제한/동작 |
| --- | --- |
| 저장 HTML 조각 | 최대 24 KiB |
| 조회 응답 HTML 합계 | 최대 48 KiB, 최대 40조각 |
| 목차 | 문서 뷰어에서 최대 80개씩; 검색 미리보기에는 보내지 않음 |
| 원문 줄 번호 보기 | 최대 16 KiB씩, UTF-8 문자 경계 보존 |
| 브라우저 | 현재 페이지로 교체; 지나간 페이지 본문을 무제한 누적하지 않음 |
| 문서 간 이동 | 먼저 메타데이터만 조회하고 해당 페이지 요청; 전문 이중 전송 없음 |

일반 조회는 표시용 SQLite의 필요한 페이지를 읽는다. 큰 단일 줄의 근거 위치 확인에는 저장된 페이지 텍스트에서 일치 구간을 찾을 수 있지만, 원문 전문을 Python/브라우저 문자열로 다시 올리지 않는다. 원문 보기에는 `sqlite3.blobopen`의 부분 읽기를 사용한다. 짧은 `substr(source)` 쿼리도 SQLite 내부에서 전문을 메모리에 올릴 수 있어 사용하지 않는다.

브라우저는 `ServerDocument`에서 제한된 HTML을 DOMPurify로 다시 검사한다. `id/name/src/style`과 실행 가능한 태그·속성을 허용하지 않는다. 링크는 현재 문서/워크스페이스의 명시적 이동으로 처리한다. 본문 전체를 파싱하는 이전 `markdown-document.ts`와 `useEvidenceSnapshot.ts`는 삭제했다.

## 4. 버전·권한·실패 처리

- 매 요청에서 기존 워크스페이스/자료 버전/원본 접근 권한을 확인한 뒤 표시 캐시를 읽는다.
- 캐시는 문서 버전 ID·내용 해시·표시 엔진 버전으로 구별한다. 원본 문서·검색 인덱스는 덮어쓰지 않는다.
- 워크스페이스 삭제/문서 버전 정리 시 해당 표시 캐시도 정리한다.
- 요청 취소, 다른 워크스페이스의 응답, 늦게 도착한 이전 응답을 차단한다.
- 준비 실패/시간 초과에는 재시도를 안내한다. 잘린 검색 조각을 Markdown으로 대신 표시하지 않는다.
- 큰 표·문단을 나눈 경우 부분 표시임을 밝히고 이전/다음 구간을 제공한다. 원문이 잘못된 경우 문장을 지어내 고치지 않는다.
- 호환성을 위해 명시적 페이지 옵션이 없는 기존 원문 API는 남아 있지만, 서비스의 문서 화면은 모두 페이지 옵션을 사용한다.

## 5. 구현 위치

- `rag/meetingbot_rag/markdown_views.py`: 구조 인덱스·서버 렌더링·안전한 페이지 분할·지수 확장·부분 읽기.
- `rag/meetingbot_rag/services/retrieval.py`: 권한/버전 확인, 캐시 검증, 별도 생성 프로세스.
- `rag/meetingbot_rag/services/ingestion.py`: 등록 시 준비.
- `frontend/src/features/rag/useDocumentPage.ts`: 제한된 페이지 조회·취소·범위 검증.
- `frontend/src/features/rag/components/ServerDocument.tsx`: HTML 안전성 검사·표시·링크 이동. Markdown 파싱 없음.
- `frontend/src/features/rag/workspace/EvidencePanel.tsx`: 구간 이동·목차 페이지·원문 부분 보기.

## 6. 5 MiB 합성 문서 측정

`rag/.venv/bin/python scripts/markdown_benchmark.py`로 재현 가능하다. 실제 문서나 외부 모델을 사용하지 않는다.

| 측정 | 결과 |
| --- | ---: |
| 원문 UTF-8 크기 | 5,245,872 bytes |
| 최초 서버 준비 | 약 1.16초 |
| 최초 작업 프로세스 최대 RSS | 약 78 MiB |
| 표시 인덱스 추가 디스크 | 약 15.8 MiB |
| 준비 후 조회 30회 중앙값 | 약 1.42 ms |
| 준비 후 조회 p95 | 약 1.54 ms |
| 조회 루프의 Python 추가 할당 최대 | 약 98 KiB |
| 미리보기 응답 전체 JSON | 4,489 bytes |
| 원문 전문 대비 응답량 감소 | 약 99.91% |

이는 로컬 디스크 측정이며 인터넷 지연이나 모든 Markdown 문서의 성능을 보장하는 수치가 아니다. Markdown 구조가 복잡할수록 최초 준비 비용은 커질 수 있다. 별도로 5.28MB짜리 단일 문단, 거대 표/셀/목록/코드, 원문 전체의 부분 조회 후 무손실 재조합을 검사한다.

검증 명령:

```sh
rag/.venv/bin/python -m pytest rag/tests/test_markdown_pages.py rag/tests/test_document_viewer.py rag/tests/test_rag.py rag/tests/test_uploads.py rag/tests/test_llm_management.py -q
npm --prefix frontend test
npm --prefix frontend run build
node scripts/markdown_integrity_smoke.mjs
node scripts/rag_upload_viewer_smoke.mjs
rag/.venv/bin/python scripts/markdown_benchmark.py
```

브라우저 테스트도 단순히 HTML을 모킹하지 않고 실제 Python 표시 엔진을 통해 생성한 결과를 사용한다.

배포 검증: 백엔드 90개·프런트엔드 50개 테스트, 전용 Markdown/업로드 브라우저 검사, 실서비스 레시피 목차 확인을 통과했다. 실서비스 검색 미리보기 6건은 각각 약 1.6–3.1KB였고, 전문 조회 요청은 0건이었다. 문서 이동·모바일 목차·원문 페이지도 확인했으며 기존 워크스페이스 3개와 모델 설정은 유지했다. 외부 모델 호출은 하지 않았다. 실제 별도 외부 기기 검증은 아니며 기존 HTTPS 주소를 사용한 브라우저 검사다.

참고: [markdown-it-py 처리 방식](https://markdown-it-py.readthedocs.io/en/latest/using.html), [서버 HTML 정제](https://bleach.readthedocs.io/en/latest/clean.html).
