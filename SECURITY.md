# Security

Do not publish credentials, real meeting documents, snapshots or question logs in issues. Describe suspected vulnerabilities using synthetic fixtures and the affected module/version. A public vulnerability-reporting address has not been configured; contact the repository owner privately before disclosure.

STT and RAG share visitor, administrator and superadministrator roles with an allowlisted server directory model. Keyless visitor sessions are enabled by default, including on normal instances. Visitors can access their own STT records and search shared RAG material; administrative operations still require an appropriate key. Set both `STT_KEYLESS_LOGIN=false` and `RAG_KEYLESS_LOGIN=false` for key-only access. The isolated public demo retains its separate data and quotas; see `docs/public-demo.md` and `docs/keyless-login-and-events.md`. It must not serve the source directory as a static filesystem. Keep the backend loopback-only and use authenticated HTTPS ingress. See `docs/rag/security.md` for session, CSRF, file descriptor, retention and external LLM boundaries.

STT and RAG run as separate services. Do not rotate, remove or upload another module's keys as part of diagnosing RAG. The existing STT key is the superadministrator bootstrap credential. Both services use the same revocable hashed key registry and browser session store.

Microphone recordings, uploaded audio, transcripts, exports and meeting analysis results are private to their owner for every role, including the installation superadministrator. Shared-document management does not grant access to another account's audio records. Records without an owner remain inaccessible through user APIs. Durable STT-to-RAG delivery also requires a separate persistent service secret from the shared access database; the installation key and an internal-request header alone cannot impersonate that channel. This API boundary does not restrict an operating-system administrator who can read the application's database files.
